## 0. 核心结论速览

1. **国家层面"标准 + 基线接口"双轨制**：编码标准由全国统一（15 项业务编码标准，数据库动态维护平台 code.nhsa.gov.cn 运营）；定点医药机构接口以国家《医疗保障信息平台定点医药机构接口规范（基线版）》为基准（引用编号 XJ-K01-2020），由各省医保局在此基础上发布**省级版本**并持续迭代（如湖北 V1.1.85、湖南 V1.1.31、海南 V2.65 等）。【已查证】
2. **接口风格高度统一**：HTTP POST + JSON（UTF-8），交易编号（infno）4 位数字编号体系（如 9001 签到、2207 门诊结算、2304 住院结算、4101A 结算清单上传、3202 对明细账），报文含 INPUT/OUTPUT 节点 + 签名节点。【已查证】
3. **安全与信创要求明确**：网络接入强制专线/专网 VPN/VPDN（禁止互联网 VPN），传输层与业务层普遍要求国密算法（SM2 非对称、SM3 签名摘要、SM4 对称加密/数字信封），配合数字证书（UKey）双向认证。【已查证】
4. **对 HIS 工程化影响**：医保接入应作为独立适配模块（适配器模式）设计，目录数据（1301-1321）本地增量缓存、结算异步对账（3201/3202）、冲正（2601）与幂等设计是上线稳定性的关键。【已查证（接口存在）＋工程建议】

### 2.2 门诊结算（挂号、诊疗、收费、退费）

典型链路：**2201 门诊挂号 → 2203 门诊就诊信息上传 → 2204 门诊费用明细上传（可多次）→ 2206 门诊预结算 → 2207 门诊结算 → （退费时）2208 门诊结算撤销 / 2205 费用明细撤销 → 2202 挂号撤销**。
- 门诊结算按"先明细后结算"组织，费用明细可增量上传、撤销。【已查证，湖北 V1.1.16 接口说明】
- 退费策略：已结算先做结算撤销（2208），再撤销明细（2205）；未结算直接撤销明细。【工程经验＋接口定义，已查证接口存在】

### 2.3 住院结算（入院登记、费用上传、出院结算、预结算）

典型链路：**2401 入院办理 → 2301 住院费用明细上传（每日/按需，可多次）→ 2303 住院预结算 → 2304 住院结算 → 2402 出院办理 → 2305 住院结算撤销（退费时）→ 2404 入院撤销**。
- 入院/出院信息变更走 2403/2405；就医特殊属性（如工伤、生育、单病种标识）走 2406/2407。【已查证，基线版接口列表】

### 2.4 医保目录匹配（药品/诊疗/耗材对照）

- **目录获取**：1301-1321 系列按"本地最大版本号"增量下载（西药中成药、中药饮片、医疗服务项目、医用耗材、疾病诊断、手术操作、病种目录等），支持 9102 文件下载大批量数据。【已查证】
- **目录匹配**：1316 医疗目录与医保目录匹配信息查询、1317 医药机构目录匹配信息查询（HIS 本地项目 ↔ 医保目录映射关系）、1318 限价、1319 先自付比例。【已查证】
- **对照上传**：3301 目录对照上传（HIS 把本院项目与医保编码做对照后回传医保）、3302 撤销。【已查证】
- 实际业务中 HIS 需维护三张核心映射表：**收费项目↔医疗服务项目编码、药品↔医保药品编码（含 27 位耗材编码）、诊断↔医保版 ICD 编码**。【工程建议】

### 2.5 医保电子凭证（扫码/刷脸身份核验）

- **标准**：《医疗保障信息平台 便民服务相关技术规范》GB/T 45938—2025（推荐性国标，2025-08 发布，2026-01-01 实施），国家医疗保障领域首项国家标准。规定医保码（医保电子凭证）、医保移动支付、医保电子处方、个人医保信息授权查询的接入方式、功能、性能与安全要求。【已查证】
  - 国家医保局发布页：http://www.nhsa.gov.cn/art/2025/8/12/art_14_17556.html
  - 陕西省医保局转发：http://ybj.shaanxi.gov.cn/sy/ybyw/gjybdt/202508/t20250812_3554175.html
- **技术机制**（依据清远市公开的《关于开展医保电子凭证应用工作的通知》，2019-12，用于理解机制）：
  - 电子凭证 = 基于证件类型、证件号码、姓名等基础信息，采用 **SM4 加密 + SM3 签名** 产生的 64 位标识码；激活后生成二维码。【已查证（地方版文档）】

  - 来源：http://www.gdqy.gov.cn/attachment/0/2/2180/966534.pdf

## 3. 对接流程要点

### 3.1 典型对接全流程（HIS 视角）

```
① 机构准入：与当地医保经办机构签约定点 → 申请机构代码（定点医疗机构代码，国家赋码）
② 网络接入：向运营商申请专线/专网 VPN/VPDN（禁止互联网 VPN），部署端点安全设备（国密 VPN 网关），与互联网物理隔离
③ 密钥/证书：申请数字证书（UKey）、SM2 密钥对、SM4 对称密钥（通常由医保经办下发或在业务中台注册）
④ 联调准备：获取本地医保局最新版《定点医药机构接口规范》，搭建联调/测试环境（模拟器或测试前置机）
⑤ 每日运行（签到会话）：9001 签到 →（业务期间）→ 9002 签退
⑥ 基础数据初始化：1101 读卡 → 1301-1321 目录增量下载 → 本地目录缓存 → 3301 目录对照上传/1316 匹配查询
⑦ 门诊业务：2201 挂号 → 2203 就诊信息 → 2204 费用明细上传 → 2206 预结算 → 2207 结算 → 打印结算单
   住院业务：2401 入院 → 2301 费用明细上传（多次）→ 2303 预结算 → 2304 结算 → 2402 出院
⑧ 异常处理：网络超时/未知结果 → 2601 冲正；结算后退款 → 2208/2305 结算撤销 + 明细撤销
⑨ 对账清算：日终/月终 3201 对总账（不平走 3202 对明细账）→ 3203 清算申请 → 3204 撤销（如需）
⑩ 数据上报：4101A 结算清单批量上传（出院后 3 个工作日内）→ 3605/3606/3607 分组与质控查询
```

### 3.2 关键数据结构与报文格式【已查证】

- **传输协议**：HTTP/HTTPS，POST；数据格式 JSON（UTF-8）；部分地区/旧系统为 XML 或 WebService（历史遗留）。【已查证，浙江医保支付门户规范明确 JSON/SM3/SM4：https://file.m12333.cn/upfile/download/a5e4c02b-10ec-554d-6a6c-7debc5847745.pdf 】
- **报文骨架**（基线版接口规范第 4 章）：
  - 输入报文：`infno`（交易编号）、`msgid`（消息 ID，唯一）、`mdtrtarea_admvs`（就医地医保区划）、`insuplc_admdvs`（参保地医保区划）、`recer_sys_code`（接收方系统代码）、`dev_no`（设备编号）、`dev_safe_info`（设备安全信息）、`signtype`（签名类型）、`sign`（签名值）、`input`（业务数据节点）、`data`（业务明细，数组）。

## 4. 省级/地方医保平台差异

### 4.1 国家平台与省平台的关系【已查证】

- 国家医保局建设全国统一的**国家医保信息平台**（14 个子系统，含核心业务区），各省建设**省级平台**接入国家骨干网；医保数据"纵向全贯通"。
- 编码标准全国统一（15 项 + 扩展），**接口规范国家出基线版**（XJ-K01-2020 → 基线版 V1.1.85 → 国家已下发 V1.2.01），各省在此基础上**裁剪/扩展**成省级版本下发本地机构。
- 浙江案例：过去 54 套割裂系统，2022 年 3 月"智慧医保"全域接入国家平台。【已查证，南方周末报道 http://m.toutiao.com/group/7305460791761814016/ 】

### 4.3 地方差异的常见处理方式【工程建议】

1. **以"接入地省级医保局最新发文"为唯一事实源**，国家基线版仅作参照；接口文档通常由医保经办机构直接下发（含 PDF 规范 + 联调环境参数）。
2. **配置化 + 适配器**：把接口差异（URL、签名算法、字段映射、版本号）收敛到配置层与适配层，避免业务代码随版本漂移。
3. **版本兼容**：接口规范半年一版是常态，升级节奏与医保局联调窗口对齐，HIS 侧预留字段扩展与多版本并存能力。

## 6. HIS 接入医保的工程化建议（重点）

基于本报告查证结果与本公司"民营医院 + 二级以下公立医院 SaaS 门诊版"的业务定位，给出以下工程建议：

### 6.1 架构：独立"医保适配模块"，与业务解耦

- 新增后端模块（NestJS 建议 `insurance/` 子域），**不侵入现有收费/挂号业务链路**；业务侧只依赖内部接口（`InsurancePort`），由适配器实现具体医保平台协议。
- 模块内部划分：
  - `protocol/`：报文构造、签名/加密（SM2/SM3/SM4）、HTTP 传输（含超时/重试/冲正策略）；
  - `adapter/`：各省/各版本适配器（实现统一端口，隔离 infno、字段、签名差异）；
  - `catalog/`：目录下载与本地缓存（1301-1321 增量同步）；
  - `settle/`：门诊/住院结算状态机（预结算→结算→撤销→冲正）；
  - `recon/`：对账（3201/3202）与清算（3203）异步任务；
  - `list/`：结算清单（4101A）生成与批量上传。

### 6.2 适配器模式 + 配置化

- 定义统一业务端口（`checkin / uploadFeeDetail / preSettle / settle / reverse / queryCatalog / uploadList / recon` 等），每个省/版本实现一套适配器，**通过配置切换**（url、infno 映射、签名算法、字段映射表）。
- 字段差异用映射表（HIS 字段 → 医保字段）管理，避免硬编码；版本升级只加新适配器，不回改业务代码。

### 6.3 本地目录缓存（关键性能点）

- 1301-1321 目录采用"本地最大版本号"增量下载：建 `insurance_catalog` 表 + 版本号表，启动/每日定时拉取增量，**目录数据全部落库**（不能实时透传，结算高频场景对医保目录查询延迟敏感）。
- 目录对照（3301/1316/1317）在 HIS 端维护映射表，上线前完成药品/项目/诊断对照初始化，未对照项目在收费端前置拦截提醒。

### 6.4 异步对账与幂等设计

- 每笔医保交易落 `insurance_txn` 流水表：msgid（消息 ID，唯一）、infno、医保交易流水号、各支付分项金额、状态（初始化/已发送/已确认/已冲正/对账差异）。
- **幂等**：同一业务动作复用 msgid（或业务单号+动作），避免超时重发造成重复结算；重试策略：超时后先查结果/冲正（2601），不盲目重发结算。
- **对账任务**：每日定时 3201 对总账，不平触发 3202 对明细账 + 下载明细文件比对；差异自动标记、人工复核清单导出。月终配合 3203 清算申请。
- 建议为门诊版先做"日终自动对账 + 异常告警"，再逐步上"旬/月清算"。

### 6.5 结算状态机与异常处理

- 状态机：`待结算 → 预结算 → 已结算 → 已撤销/已冲正`；预结算结果仅展示，不落账。
- 网络异常/超时：一律"先查询后冲正"策略（查不到结果再 2601 冲正），并保留现场报文日志（docs\日志 归档）便于与医保局联调排查。
- 退费流程严格走"结算撤销 → 明细撤销 → 挂号撤销"顺序，防止基金回冲不一致。

### 6.6 安全与信创

- 网络：按接入地要求申请专线/专网 VPN/VPDN，机构侧端点安全设备与互联网物理隔离（服务医院为民营/基层机构时，通常选 VPN/VPDN 或运营商专线，预算可控）。
- 密码：准备 **SM2 证书（UKey）+ SM3 签名 + SM4 加密** 的国密实现；Java 侧用 BouncyCastle（含国密算法）或 GmSSL，注意密钥由医保经办下发/注册，本地只存密文与引用。
- 签名验签：严格校验返回报文签名，防中间人篡改；日志脱敏（身份证、手机号等）。

### 6.7 测试与验收

- 医保经办通常提供**联调测试环境 + 测试用例集**（签到、读卡、目录下载、结算、撤销、对账全流程），HIS 侧建议自建**医保模拟器**（基于官方规范示例报文）供开发与回归。
- 验收关注：真实环境小额试结算、退费场景、对账差异为 0、故障注入（断网/超时）下冲正正确性。
- 参考规范第 7/8 章 Java 示例代码与报文样例搭建联调脚手架。

### 6.8 与一期 SaaS 门诊版的衔接

- 一期无医保：收费表结构需预留医保字段（医保交易流水号、结算 ID、基金/个账/现金分项、报销比例），避免二期大改表。
- 多租户注意：不同医院可能接入不同省份/统筹区医保，**医保配置必须按租户（医院）隔离**（省、统筹区、接口版本、证书、目录缓存实例）。
- 门诊版二期优先级建议：基础信息（读卡+目录）→ 门诊结算（挂号/明细/预结算/结算/撤销）→ 电子凭证扫码 → 对账 → 结算清单上传 → 住院（如有住院院区）→ DRG/DIP → 电子处方/进销存。
